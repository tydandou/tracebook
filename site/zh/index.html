持久项目记忆

让项目记忆跨越对话。

Tracebook 为 Codex、Claude Code 和其他编程 Agent 提供本地、基于证据的项目记忆；无需服务器、数据库，也不会向你的业务仓库写入文件。

## Current

退款最多重试两次，

每次超时 3 秒。


Evidence: src/refunds.py:L18

验证→捕获→复用

问题

新对话，不应该等于重新调查。

源代码会保留下来，但围绕代码形成的判断经常随着会话消失。Tracebook 只保存值得复用的结论，并保留以后质疑这些结论所需的证据。

01

减少重复摸索

Agent 工作前加载相关结论，无需反复重读同一套架构、事故根因和业务规则。

02

每个事实都能溯源

当前结论必须声明证据。源文件缺失或晚于知识更新时间时，健康检查会提出复核提示。

03

业务仓库保持干净

知识保存在 ~/.tracebook，无需记忆目录、后台进程、向量数据库、Hook 或仓库配置。

一个任务，两次会话

让 Agent 把经过验证的上下文带到下一次工作。

Agent 负责判断哪些结论值得保存；本地 Runner 负责项目身份、存储、版本历史、事务和健康检查。

开始工作前

只读取相关知识

解析当前项目，使用有边界的检索返回相关且仍然生效的知识，不把整个知识库塞进上下文。

完成验证后

捕获持久结论

聊天原文和未经验证的猜测不会成为当前事实。稳定 ID、证据、范围、状态和历史共同约束写入。

下一次会话

从证据开始

Agent 先取得当前结论；当任务需要深入确认时，再回到结论引用的源码、配置或测试。

受治理的记忆

不是聊天记录仓库。

知识可以处于 Current、Pending、Deprecated、Superseded 或 Historical 状态。写入具备事务保护，正常读取使用已提交快照。

  • 项目、领域和可复用工程模式三种范围
  • 同一 Git remote 的多个 clone 共用稳定项目 ID
  • 通过显式系统与关系约束跨项目检索
  • Light、Regular 与显式 Deep 健康流程
知识生命周期
CURRENT     当前生效
   │
   ├── revise → 保留版本历史
   │
   ├── SUPERSEDED → 指向替代知识
   │
   └── DEPRECATED → 不再适用

PENDING     已知但尚未确认
HISTORICAL  仅在显式请求时读取

选择适合的记忆模型

Tracebook 有意保持明确边界。

它不是任务管理器、语义搜索引擎，也不替代宿主的指令文件。以下对比说明这些边界在什么情况下有价值，以及什么时候另一种方案更合适。
